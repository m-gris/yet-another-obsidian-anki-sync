# Evolvability of `yet-another-obsidian-anki-sync`

*Written 2026-08-25, from a read-only pass over the repository and the installed AnkiConnect add-on. Anki was not running, so **no live probe was performed in this pass**. Every claim about Anki's behaviour is labelled **VERIFIED** (read in source I cite, or recorded as a live measurement I recovered and cite) or **UNVERIFIED** (asserted in this repo with no citation, or never measured at all). Two of the system's most load-bearing beliefs turn out to sit in the second column.*

---

## 1. The one-paragraph answer

> **CORRECTION, 2026-08-25, made after this document was first committed.** This section opened
> “far more evolvable than it feels” and said the owner’s fear was “aimed at the wrong layer”.
> Both were wrong to lead with, and both contradicted §4 of this same document, which had it
> right. The error is recorded rather than quietly edited away, because it is the exact failure
> this project keeps catching everywhere else: **a true statement chosen in place of the operative
> one.** It is true that nothing here destroys history. It is not true that the fear is misplaced
> — a card whose binding you cannot reattach is a card you will never review again, and past a
> few hundred orphans nobody reattaches anything by hand. The paragraph below now leads with the
> operative fact. Nothing else in the document changed; §4 said this all along.
>
> _Two process notes for whoever runs the next one of these. Each of the six lenses was given an
> adversary; **the synthesis was given none** — so the one artifact anybody would actually read
> was the only unverified output in the run. And a document of this size is consumed through
> whatever summary reaches the reader, which makes choosing what to surface part of the
> deliverable rather than a courtesy afterwards; choosing the comfortable section wastes the
> exercise that produced it._


**Nothing in this system destroys review history, and almost nothing in it lets you keep review history attached to a card you have reworded.** Those are two different facts, and only the second one governs what the system is like to use. Of the twenty-one operations the tool can perform, none deletes — `anki/Anki.scala` declares no `deleteNote`, no `deleteCards`, no `deleteModel` (VERIFIED, enumerated: `anki/Anki.scala:158,161,172,175,197,221,236,253,261,269,271,273,279,319,327,329,337,339,341,361,370`). Tags are additive and subtractive within the tool's own three prefixes; field updates and deck moves never touch a card row; suspension is reversible and automatic. The binding is a tag, and **a tag is cheap to rewrite forever** — which means re-keying a collection of five thousand cards costs the same *per card* as re-keying eighteen, and costs *no history at all*. Almost every hazard in this system costs the **findability of a binding** rather than the accumulated value behind it — but findability IS the value, once the collection is past the size at which anybody reconciles by hand. §4 of this document states the consequence and this paragraph originally did not: a detached history is “technically preserved and practically abandoned, which is a slower version of losing it”. Renaming a marked heading detaches one card; renaming an H1 or any ancestor detaches every card beneath it; changing a card’s TYPE is refused outright in every case except within the `cdd/` family. Those are the ordinary gestures of revising your own notes — which is what learning looks like — so **revision, not deletion, is this system’s cost centre.** With that said, the structural finding stands and it does matter: **the accumulated layer is exposed in exactly two places, and neither of them is identity.** (a) Operations that change a note's *card set* — retyping across template counts, flipping a gate field so a card's front renders blank, and unlabelled cloze ordinal drift — because scheduling hangs off `(note, ordinal)` and all three move ordinals under a note whose key never changed. (b) A human acting on a state the tool created and never reported — `Tools > Empty Cards` today, `prune` tomorrow. Everything else is a re-binding problem, and re-binding is exactly what this design made cheap on purpose. **There is one confirmed exception, live today**, and it is a defect rather than a design consequence: a note that was orphaned and comes back on a *different note type* is retyped, has its `orphaned::` tag dropped by that write, and is **never unsuspended** — leaving a card with its full review history permanently out of rotation and invisible to every report (§3.1). That is the only path I can trace end to end in which accumulated value is permanently removed from use by this tool's own writes.

## 3. Where the system is already fragile

Ranked by *irreplaceable history at risk × silence*. "Live today" means reachable at eighteen cards; "at scale" means the mechanism exists but only bites when the collection is large.

### 3.1 Retype over a returning orphan strands a card, permanently and silently — **live today**

The only path I can trace in which this tool permanently removes accumulated value from use.

Chain, every link read: a heading goes away → `Flag` tags `orphaned::` and suspends every card (`plan/Executor.scala:363-365`). The heading comes back **on a different note type** → `Planner` takes the `Retype` branch, and that branch **rebuilds the owned tag set from scratch**, which its own comment says is "what makes a separate `Unflag` unnecessary here… any `sha::` or `orphaned::` it held before is gone by the same write" (`plan/Planner.scala:305-312`). The `Unflag` that *would* have unsuspended it is computed only in the sibling `else` (`plan/Planner.scala:348-349`). The executor's `WillApply` arm calls `changeNoteType`, then optionally `changeDeck`, and **never `unsuspend`** (`plan/Executor.scala:331-339`). A live probe recorded that a retyped note keeps its card's `queue` (`RECONCILER-SHAPE.md:43`) — so the card **stays suspended**.

Result: a card with its full review history, correctly keyed, correctly typed, in the right deck, carrying no `orphaned::` tag — permanently out of the review queue. `Report.parkedNote` counts only tagged notes, so nothing reports it. The planner sees content and deck matching, so no later run repairs it. This is precisely the state `plan/Executor.scala:367-371` argues `Unflag`'s ordering exists to prevent ("an untagged live card is indistinguishable from a healthy one"), reintroduced through the sibling branch.

Preconditions, stated honestly: it needs `--migrate-note-types` (under `Defer` every retype is partitioned out before execution, `plan/Executor.scala:206-214`), and it needs a note-type change that passes the gate — `Obsidian Basic` and `Obsidian Cloze Sequence` are both standard with one template, so a `#flashcard` heading that was orphaned and returns as `#flashcard/sequence` qualifies. The scale version is worse and needs no unusual authoring: a marker-vocabulary change or a manifest rename that retypes many notes at once, sweeping up whatever is parked.

`plan/Retyping.test.scala:383-399` pins the tag-drop as intended and asserts nothing about suspension.

### 3.2 Unlabelled cloze ordinal drift — **live today**, silent, and its documented consolation does not exist

`Cloze.number` assigns each unlabelled group the lowest number no label has claimed, in order of first appearance (`extract/Cloze.scala:200-230`). Insert one `==highlight==` earlier in an existing `#flashcard/cloze` section and every later unlabelled group renumbers. The section is one `CardKey`, so nothing about identity moves: the planner sees a hash mismatch and emits an ordinary `Update`; the `Text` field is rewritten with different `cN` assignments.

The failure *direction* matters and is worse than "one card loses its history": an insertion **rotates**. Card ordinal 0 keeps old-c1's history under new-c1's content, ordinal 1 keeps old-c2's history under old-c1's content, and only the single highest new ordinal is historyless. Every deletion's history is misattached to a neighbour.

**Two things I want to be precise about.** First, the Anki half is UNMEASURED — that existing cloze cards keep their ordinals through a `Text` rewrite is asserted nowhere in this repository. Second, and this is the sharper finding: `model/CardSpec.scala:42-46` and `docs/CARD-MODEL.md:251` both promise that editing an unlabelled deletion's text "retires the key: the card starts over and the old one is flagged as an orphan, visible in the prune list." **No such thing happens.** Orphan flagging operates on `CardKey`s, and a `CardKey` is one per *section*. I grepped all of `plan/` for cloze awareness: `ClozeGroup`, `ClozeDeletion` and ordinals appear nowhere in the planner — the only ordinal reasoning in `plan/` is `Retyping`'s discussion of note-type shapes. A retired cloze group produces no `Flag`, no `orphaned::` tag, and no prune-list entry.

Nothing tests the property that carries the history: `extract/Extractor.test.scala:552-564` has a test titled "a labelled group's identity survives a text edit; an unlabelled one does not", but it asserts on **groups**, not on ordinals across an insertion.

### 3.3 Narrowing a marker parks a card in `Empty Cards`' sights, and nothing counts it — **live today**

`cdd/3way` → `cdd/2way` is the same note type with a gate field flipped; card 3's whole front is inside `{{#ThreeWay}}`. It plans as an ordinary `Update`. The gate fields are deliberately **inverted** (empty means the old behaviour) precisely so that notes predating a field do not fall into this, and `model/Marker.scala:280-284` says why in as many words — "Anki's Tools > Empty Cards would offer to DELETE cards holding real review history". So the project understands the hazard exactly.

What is not built is any report of it. The tool creates the condition, never counts it, and cannot undo it once a human runs the bulk tidy. At eighteen cards a stray blank is noticed by eye; at thousands it is a maintenance chore performed in bulk.

**The Anki half of this is UNVERIFIED — repo-asserted, uncited.** Whether Anki keeps the card, whether `Empty Cards` takes the revlog with it, and whether re-widening the marker restores the card intact are all unmeasured. The reversibility claim that makes this "a missing report" rather than "a live loss" rests entirely on that unmeasured behaviour.

### 3.4 A partially materialised vault flags and suspends the whole collection, and the run reports success — **live today; damage scales**

`.obsidian/` arrives before the notes do on Dropbox or iCloud. `VaultRoot.at` passes. The walk yields zero (or few) files. A file that is simply *absent* produces no failure, and `VaultScan.from` degrades to `PartialScan` only when a failure carries `OrphanShelter.Unknowable` — so this is a **complete scan of nothing** and `canInferOrphans` is true (`plan/VaultScan.scala:237-243,277-279`). Every observed note is flagged and suspended. The verdict is `Clean` and the exit code is 0.

`docs/CARD-MODEL.md:212-214` accepted this for v0 on an explicit condition: "It stops being cheap the moment flagged cards are also **suspended** — a mistimed sync would then empty the review queue until the next correct run. Revisit before or alongside that work." Suspension shipped (HANDOFF.md:322). **The condition has expired and the acceptance was not revisited.** `cli/VaultRoot.scala:22-25` says plainly "Nothing here helps with that."

No history is destroyed and the next correct run unflags and unsuspends. Three honest qualifications: the run that *does* the damage is the silent one (`Report.plan` prints `N flag as orphaned`, and the word "suspend" is not in it — `cli/Report.scala:383`); every run *afterwards* prints the parked count and the word "suspended" (`cli/Report.scala:108-117`, and `Plan.parked` is observed *before* this run, `plan/Planner.scala:61,414`); and the tool prints `notes: N` immediately before the plan for exactly this reason (`cli/Main.scala:838-856`), so it is visible to an attending human and invisible to an unattended one.

**Note what `README.md:342-344` promises and does not deliver: "The run reports what it suspended."** It does not.

### 3.5 Fan-out: one edit, a file's worth of orphans — **live today, damage scales with the vault**

There are **three** channels by which one edit reaches many cards, not two.

- **The ancestor chain.** The key path is `ancestors :+ segment` (`extract/Extractor.scala:143,150,158`), so the file's `# H1` is a segment of every key beneath it. The golden's first record is `src::fix-body-shapes::body%20shapes/layers%20of%20the%20epidermis` (`extract/golden/fixture-cards.txt:28`) — `body shapes` is the H1.
- **The frontmatter `id`.** Half of every key in the file (`model/CardKey.scala:76-80`).
- **`Context`.** The breadcrumb is the *whole location* — folders, file name, heading chain (`extract/CardContext.scala:62-70,93-102`) — and `contentHash` covers every field (`plan/Planner.scala:146-155`). So a folder move or a file rename rewrites the `Context` field of every card in the file. Measured: one change to how `Context` is computed moved all 55 golden cards and planned **16 updates** on Marc's real vault (IN-FLIGHT.md:15-17).

The first two are *tied* for the largest blast radius, and the H1 is the likelier of the two — the commonest Obsidian convention is a file whose H1 restates its own name, which `dummy-vault` does in all twelve files (`extract/CardContext.scala:118`). So the natural gesture "rename the file, bring the title into line" hits the maximum-blast-radius edit whether or not it touches the `id`. Costs no history; costs every binding in the file, reported as two bare counts.

### 3.6 ~~The premise under the never-delete design is unverified~~ — **SETTLED 2026-08-25**

Kept rather than deleted, because what it ranked was how much hangs on the answer, and that is
unchanged: the entire flag-then-prune ruling substitutes suspension for deletion, so if unsuspend
did not restore scheduling exactly, §2, §3 and §7 of this document would need rewriting rather
than amending.

**It was measured and it holds.** See the `suspend`/`unsuspend` row in §2 for what was compared.
The measurement took five minutes and had not been run in the six days since suspension shipped.

Two things about how it was measured are worth carrying forward, because both are the failure
this project keeps finding rather than a curiosity. The first attempt compared ten columns and
reported every one identical — three of them, **including `interval`, the one that matters most**,
were `None` on both sides, because `cardsInfo` returns `interval` and not `ivl`. A passing
measurement of a field nobody read. The second attempt names the real columns and **aborts** if
any is `None` on both sides, so it cannot pass by comparing nothing. And the recorded footgun was
honoured: `getReviewsOfCards` returns empty for card ids passed as strings and real entries for
the same ids as integers, erroring on neither.

*Aside, VERIFIED by reading `__init__.py:1041-1046`:* the add-on's own idempotence pre-filter is
`for card in cards: if self.suspended(card) == suspend: cards.remove(card)` — mutation while
iterating, so it skips every other already-suspended card. Harmless here, since the scheduler is
still reached with the rest, but it is not the clean no-op `anki/Anki.scala:357-359` describes.

### 3.7 Divergence between Anki and the vault is never detected — **at scale**

`fieldsDiffer` is `!existing.recordedSha.contains(sha)` (`plan/Planner.scala:339`) — the vault's hash against a tag *the tool itself wrote*, never against the note's actual fields. A field hand-edited in Anki changes neither side. The note diverges permanently, unreported.

**The fix is already paid for.** `ObservedNote.fields` (`anki/Anki.scala:88-93`) is decoded on every run from the bulk `notesInfo` the observer already makes, and consumed by *nothing* — every `.fields` use in `plan/` is a write of `spec.fields`. This is a produced-but-never-consumed value sitting in memory at the moment the decision is taken. Costs no history; costs the truth of the word "derived", and it poisons the content-hash repair hint, which fires only when exactly one card matches.

### 3.8 Filtered decks cross the reconciler's path in two directions, both unestablished — **at scale**

Filtered decks over tags are the design's *own* stated study-scope mechanism (`README.md:318-319`). What `getDecks` returns for a card gathered into a filtered deck, and what `changeDeck` does to its `odid`/`odue`, is established nowhere in this repository. Neither is what `suspend`/`unsuspend` does to such a card — and orphan flagging suspends. The collision was inventoried in only one direction in this brainstorm; it exists in both. Intermittent, therefore hard to attribute.

Related, and worth naming because a docstring asserts the opposite of the code: `Executor.firstDeckOf` observes a note's deck from `cards.headOption` only (`plan/Executor.scala:141-146`) while `changeDeck` fans the move out to *every* card. Its docstring claims "a partial move that broke that assumption would show up as a deck change on the next run rather than being silently ignored" — true only when the first card is the one that moved.

### 3.9 Orphans accumulate and nothing retires them — **at scale**

Every rename, every ancestor edit, every `id:` change adds parked notes. A parked note produces no action ever again. `Report.parkedNote` now prints a count on every run and says plainly that nothing removes them (`cli/Report.scala:108-117`, added because six sat unmentioned in a real collection under a run that printed `nothing to do`, IN-FLIGHT.md:160-170) — which is the honest version of the problem, not a fix. **The structural statement is sharper than "orphans accumulate": the system can mint bindings without limit and has no operation that retires one.** `prune` is the missing inverse of `Create`, and its absence is currently what makes everything else safe.

### 3.10 The rules that carry the preservation guarantees decay faster than the code — **standing**

The preservation rules live almost entirely in prose. `-Wconf:msg=exhaustive:e` and the mutation-tested laws hold the code; nothing holds the sentences. Two live instances, both on the history-protecting path:

- **`plan/SyncAction.scala:162-166`** — the `Flag` case's own docstring: "WHAT THIS DOES TODAY IS WRITE A TAG, AND NOTHING ELSE… that is not built: `Anki` has no suspend operation yet." It is flatly false. `Anki.suspend` is at `anki/Anki.scala:361` and `Executor` suspends at `:363-365`. The single place where the code describes the action that protects history says the opposite of what it does.
- **`model/CardSpec.scala:42-46`** — the cloze consolation that does not exist (§3.2).

## 4. The reformulation problem

### The problem, precisely

Card identity is `(frontmatter id, full ancestor heading chain)`, and a heading segment is the heading's *extracted, canonicalised text* (`model/CardKey.scala:70-80`). So the key is a projection of the very prose the author is trying to improve. Rewording is what refining your understanding looks like, and it mints a new key.

Three facts make this worse than "a rename is undetected".

1. **The blast radius is the subtree, not the heading.** Every ancestor is a key segment, including the H1 (§3.5).
2. **The content hash moves too, so it can never witness a rename.** The marked heading is a *field* on every card shape — Front (`extract/Extractor.scala:371`), Descriptor (`:421-430`), Sequence Title (`:562-566`) — and for cloze and table it is inside `Context`, which excludes nothing (`:451-455`, `:294-297`). `contentHash` covers note type plus every field in order (`plan/Planner.scala:146-155`). There is no card shape where a rename leaves the hash intact.
3. **The recovery machinery that exists reads as though it covers renames and structurally cannot.** `Planner.identityErrorFor` — which names a likely card, prints the exact percent-encoded tag, and deliberately applies nothing — is reached only from `observed.unresolved` (`plan/Planner.scala:281`), i.e. notes whose identity tag is *unreadable or ambiguous*. A renamed heading leaves a perfectly readable tag that simply matches nothing. It takes the orphan branch (`plan/Planner.scala:405-412`) and receives no suggestion of any kind.

What the tool prints for a rename is `1 create` and `1 flag as orphaned`, as bare counts, with no pairing (`cli/Report.scala:72-75`). Reconciling by hand means: infer the pairing by eye, copy the `src::` tag off the newly created note, paste it onto the orphan, delete the new note, clear `orphaned::`, unsuspend. Per card, times the fan-out — and `plan/Planner.scala:207-209` records that the tag cannot be written out by hand, because the encoding escapes spaces, slashes, colons and both Anki wildcards.

That is the tax. Nothing about it is lossy — the orphan keeps its `src::` tag, its `sha::`, its deck and its whole scheduling state, and `orphaned::{old key}` is deliberately readable in Anki's browser (base64url was rejected for exactly that reason, `model/CardKey.scala:169-171`). The history is technically preserved and practically abandoned, which is a slower version of losing it.

### The second axis: revising SHAPE, not prose

_Added 2026-08-27. Everything above and below this subsection is about revising **prose** — the key
is a projection of the wording you are trying to improve. There is a second axis, it is taxed too,
and it had one clause in this document and no analysis._

**Anki follows you on two of the three things you can change, and not the third.**

| you change | does Anki follow? | how |
| --- | --- | --- |
| the **content** of a card | yes | an ordinary `Update` |
| its **location** (folder) | yes | a deck move; scheduling untouched |
| its **shape** (which marker) | **mostly not** | a retype, and most are refused |

**And "mostly not" is worse than it sounds, because the commonest changes of mind all cross note
types.** A marker does not sit in the key, so the card keeps its identity — but the note type
underneath it has to change, and that is the operation the gate guards:

- `#flashcard/1way` → `#flashcard/2way` — *"I want this asked both ways now"*, surely the likeliest
  change of mind of all — moves `Obsidian Basic` → `Obsidian Basic (and reversed card)`.
- plain `2way` → `cdd/2way` — moves onto `Obsidian Concept-Descriptor`.
- anything → `cloze` or `sequence` — crosses cloze-ness, and that one is genuinely dangerous.

**The only shape edits that have always worked are within the concept-descriptor family** —
`cdd/1way ↔ 2way ↔ 3way` — because those are the same note type with a gate field flipped, so they
plan as an ordinary field update rather than a retype.

**That this was foreseen is visible in the design.** The gate fields exist precisely so direction
can change without a retype, and the ruling that *gate fields are inverted — empty means the old
behaviour* is there so a note predating a field does not render blank. Somebody thought hard about
shape revision INSIDE a note type and solved it. Crossing note types never got the same treatment.

**What changed on 2026-08-26**, after the growth direction was measured (see §2): the gate now
refuses only SHRINKING, so `1way → 2way` and plain-`2way → cdd` both work. Narrowing within the
`cdd` family still leaves a card behind — see the narrowing row in §2 — and shrinking across note
types is still unmeasured and still refused.

**Why this belongs beside the prose axis rather than in its own section.** Both are the same
sentence: *revision is what this system taxes.* Rewording a heading detaches a card from its
history; changing a marker is refused outright. One is silent and one is loud, and a person doing
either is doing the ordinary thing — improving their own notes.

### Candidate directions, with their real costs

**A. Exact non-`Context` field pairing, report-only.** *This is the strongest thing to come out of this brainstorm and it was nearly missed.*

The next recovery tier is usually framed as inherently fuzzy. It is not. Under **every** card shape a heading rename leaves at least one substantial field **byte-identical**: TwoField's Back is the body (`extract/Extractor.scala:372`), the concept-descriptor's Description is the body (`:423`), cloze's `Text` is the lowered body (`:451-455`), Sequence's Body (`:563`), and a table's cells come from rows, not headings. And `Context` is a *separate field* in all five note types — so an **ancestor** rename changes only `Context` and leaves every other field untouched.

So "same note id, same note type, every field but `Context` identical" is available as **evidence of the same class as `sha::`** — agreement, not a similarity score. It is confined to one frontmatter id, which `docs/CARD-MODEL.md:299` records as the key's own gift. And it costs **no additional Anki calls**: `ObservedNote.fields` is already fetched and already thrown away (§3.7). Crucially it works **retroactively** — on orphans that already exist — which no tag-based scheme can.

Costs, honestly: IN-FLIGHT.md:141-145 already records the failure mode — "two cards with identical fields under different keys trip nothing: `allowDuplicate` is on, uniqueness is by key, and nothing compares content. It also weakens the hash-based repair hint, which fires only when exactly one card matches." So it must speak only when exactly one candidate matches, and stay silent otherwise. A rename combined with a body rewrite in the same edit is still undetected. And IN-FLIGHT.md:174-176 claims tier 2 ("exact fields") is *built*; it is not — no exact-fields comparison exists in the code.

**B. An explicit `relink` command.** Turns the five-step GUI operation into one command, using only operations the algebra already has. Its preconditions are all checkable before writing: the orphan exists and holds the old tag; the shapes agree.

The honest cost that the brainstorm's own version of this option omitted: **it needs the newly-created note to go away, and the algebra has no delete** — deliberately, and `plan/SyncAction.scala:181-191` exists specifically so a future `Prune` cannot reach the executor by falling through a catch-all. So `relink` must **refuse** when the new key already has a note, and tell the human to delete it in Anki first. That keeps deletion out of the algebra and the human in the loop, and it is buildable today. What it must never do is infer the pairing — a wrong relink moves review history silently and irreversibly, which is the standing ruling (`plan/SyncAction.scala:295-318`; IN-FLIGHT.md:174-176, "anything fuzzy may only RANK candidates, never apply").

**C. An author-purchased per-heading anchor** (`#flashcard/2way/k-a7f3`), keying the card when present and falling back to the derived key when absent. Structurally the marker grammar already tolerates it: `#flashcard(?:/[\w-]+)*` is stripped from the key segment, from the display text, and from the deck-path title, at three separate call sites (`model/CardKey.scala:47,58-60`; `model/Marker.scala:393,401`; `extract/Extractor.scala:144`). Only the exhaustive `Marker.fromToken` table refuses it.

**I do not accept the argument usually offered for it.** The cloze `==N|text==` label is *not* the same act at a different granularity: the label is a card **ordinal inside a note that already exists** (`extract/Cloze.scala:13,28-34`; `model/CardSpec.scala:35-47`), not a component of `CardKey`. A cloze section keys as `(id, heading path)` like everything else — rename a cloze heading and the whole note orphans, every labelled group with it. The precedent does not transfer, and treating it as consistency is exactly the kind of unearned move this document should not make.

The case for C, if there is one, has to be made on its own terms — and there is one: the frontmatter `id` already *is* an author-written, in-markdown, load-bearing identity value (§5). Real costs: three coordinated strip sites in a codebase whose recorded scar is a stripping guard that silently went dead; copy-paste of a section becomes a duplicate-key **whole-run refusal** (`plan/Planner.scala:239-248,286`), which the current scheme also suffers but far more rarely; `docs/REQUIREMENTS.md:110`'s stated property that "the marker count in the markdown is therefore zero, and stays zero regardless of card count" is retired; it does **nothing** for ancestor headings, which carry no marker to hang a token on; and if the anchor *replaces* path structure it retires `Planner.underAFailedSection` (`plan/Planner.scala:398-411`), the prefix-shelter rule that exists because one image pasted into one table cell once flagged fifteen live cards. Finally, retroactive adoption is itself a re-key: a heading that gains an anchor while its derived key is live orphans its own card, unless an in-place rebind ships first. That is a precondition of the option, not a detail.

**D. Shorten the key — drop ancestors.** Collapses the amplification to zero, and reintroduces the exact collision the ancestor chain exists to prevent (`model/CardKey.scala:70-75`: `CAP Theorem / Definition` vs `Quorum / Definition`). It is also not uniformly expressible: a table's cards key one or two segments *past* the marked heading (`extract/Tables.scala:161-168`; `plan/Planner.scala:379-381`). **And it is on HANDOFF.md:249's do-not-relitigate list.** One correction to the brainstorm's framing: it is *not* "effectively irreversible" — the binding lives in a tag the tool owns outright and can rewrite, and both old and new keys are computable from the same vault in one pass. Conceding otherwise would concede the one thing the identity design was built to make cheap. It fails on the collision, not on the migration.

**E. Widen canonicalisation.** Cheapest thing available; the dial exists and has been turned five times (marker strip, extracted text, NFC, whitespace collapse, case fold — `model/CardKey.scala:32-40,193-215`, ruling B5 at HANDOFF.md:249). Bounded, and the bound is low: it cannot cover a genuine rewording, and every notch merges keys that were distinct. Each notch is close to one-way once history exists.

**F. Git history as rename evidence.** `docs/CARD-MODEL.md:299` already records the right insight — a renamed heading is a one-line diff, *a record of the edit* rather than an inference from two strings — and records that this survived the cut as one of two findings worth keeping. Strictly stronger evidence than similarity. Costs a workflow constraint (commit before sync) and a piece of last-synced-commit state the design has carefully avoided.

### My reading

**A, then B, and defer C until it is measured.**

A is the most promising because it is the only candidate that is *exact*, *retroactive*, *free of new observation*, *free of any markdown change*, and *free of any adoption event*. It costs a comparison over data already in memory. It converts the parked set from an archive you can see and cannot claim into a worklist. And it is licensed by rulings already made rather than needing new ones.

B makes the claim payable. Together they take the recovery cost from "a fiddly Anki operation nobody performs two hundred times" to "a chore that scales", which is the specific thing missing today.

C is the only option that makes rewording **free** rather than **payable**, and that is a real difference. But it is a one-way ratchet with a real adoption cost that grows with the collection, it does nothing for the ancestor channel — which is the *larger* of the two blast radii — and nobody has measured whether heading renames actually dominate the cost of change in this vault. That measurement is free, needs no Anki, and can be run this afternoon (§6, M1). **It is the thing that should decide C, and until it is run, C should not be decided.**

Two things stay unresolved, and I want to name them rather than paper over them. First, whether renames dominate at all: it is the most *vivid* cost, which is not the same as the largest. M1 settles it. Second, the ancestor channel has no good candidate — A pairs ancestor renames well (only `Context` moves, so the field evidence is at its strongest), but nothing *prevents* them, and the H1 is bound to the file name by convention. If M1 shows ancestor rewordings are common, the answer is probably F (git evidence covering the subtree in one record) rather than C.

## 5. The premise, examined

The premise as written is: *"Nothing generated is ever written back into the markdown… Anki is a derived artifact, so bookkeeping there is free — which is exactly what makes it unacceptable in the source."*

**What is actually true, and deserves absolute defence: the tool never writes the vault.** This is structural, not promissory. I grepped every non-test source directory for `Files.write`, `newBufferedWriter`, `PrintWriter`, `FileOutputStream`, `writeString`: the only `.write(` hits are `ByteArrayOutputStream` inside the percent-decoder (`model/CardKey.scala:236,244`), and the only `java.nio.Files` calls are existence checks and two reads. `cli/VaultRegistry.scala` makes read-only structural — no encoder, no serialiser. Nothing writes the golden either. That invariant is real and I found no place where it produced sloppy code; the opposite.

**What is not true as stated: the markdown already carries a generated-looking, load-bearing identity value.** The frontmatter `id` is half of every key in its file, must never change, and deleting one orphans every card the file owns (`docs/CARD-MODEL.md`, identity section; `README.md:108-109`). And the reference vault's documented id shapes include a machine-shaped `1786713776-ZMPB` alongside a bare date and an authored slug (`model/CardKey.scala:181`; `extract/Frontmatter.test.scala:126-131`). So the line is not "no identity in the source". It is "no identity **written by this tool** into the source" — which is a different and much narrower claim, and a correct one.

**Where I part company with the adversarial reading.** It argued that the premise is one sentence doing two jobs, that only the first is argued, and that the second inherits its justification by adjacency. The first half of that is right; the second half is not. The decision was argued and cut, twice: `docs/REQUIREMENTS.md:104-107` records that an in-file write-once identifier was **accepted and then superseded** ("That reasoning was sound given the options then known, but a better one exists"), and `docs/CARD-MODEL.md:299` lists *author-maintained per-heading identifiers* among eight approaches explored before rename detection was cut on 2026-08-19. What is missing is the **reasoning** for that cut, not the cut. That licenses "go find why", not "re-decide".

I also reject the consistency argument built on the cloze label. It does not hold (§4C).

**Where I land, and I am not hedging.** The premise as worded conflates a structural invariant with a design choice, and the choice is currently riding on the invariant's reputation. It should be restated:

> The tool never writes the vault. Card identity is derived from `(frontmatter id, heading path)` — a choice, not an invariant, made because it keeps the marker count in the markdown at zero regardless of card count, and revisable on evidence.

Restating costs nothing and commits you to nothing. What it changes is the *category* of the anchor question: it moves from "would violate a principle" to "is a trade that needs a number". `docs/REQUIREMENTS.md:114-143` already puts "card identity **and its binding to a note**" in the rigid column and warns against defending a taste as an invariant — and it does *not* say identity must be content-addressed. That reclassification is the whole deliverable of this section. The measurement follows in §6; the decision follows the measurement.

One thing the restatement does **not** license: a sidecar being off-limits. It is not. `docs/CARD-MODEL.md:186` and `docs/REQUIREMENTS.md:108` both bless one explicitly — "a local sidecar mapping keys to Anki note ids is a cache, not an oracle. Deleting it is harmless — it rebuilds by reading the `src::` tags back out of Anki." The zero-local-state property is a de-facto consequence of nothing needing one, not a ruling.

16. **A run ledger.** Deferred, and I want to say why rather than leave it implied: its main justification — reconstructing an aborted run — does not hold. `applyEach` wraps every action in `.attempt` and folds failures into `ExecutionFailure` (`plan/Executor.scala:255-266`), so no `AnkiError` escapes mid-write; the only `Left` from `Executor.run` comes from `Retyping.shapesOf` under `Apply`, which runs **before the first write** (`:215-218`). So `AbortedDuringExecution`'s "writing may already have begun" is over-cautious on every reachable path. The genuinely unknown case — process death or a transport `Throwable` — never reaches that branch at all; it crashes out of `IO`. A ledger's remaining justification is an audit trail, which is real but not urgent.

## 8. What we decided not to do

**A proportion-based orphan guard.** Already ruled out at `docs/CARD-MODEL.md:214` on the grounds that the proportion is a number nobody can justify. That ruling stands and I am not reopening it. The zero-card refusal (item 6) is a different claim and needs no number.

**Transplanting scheduling** — copying revlog rows and card columns from an orphan onto a new card. Mechanically reachable: `getReviewsOfCards` (`__init__.py:1647-1666`), `insertReviews` (`:1689-1695`), and `setSpecificValueOfCard` (`:993-1022`), whose guarded-key list at `:1008-1011` notably does **not** include `due` or `factor`. Rejected anyway: it writes card columns by `setattr` with `skip_undo_entry=True`, and what Anki's scheduler and FSRS do with columns or revlog rows written that way is established by nothing anyone has read. It also *duplicates* rather than moves history unless the source is destroyed — which is a deletion, the one thing the sync has ruled it never does. A scheduler-sanctioned path exists beside the raw one (`answerCards` `:1620-1634`, `setDueDate` `:1670-1672`, `forgetCards` `:1601-1610`) and is a materially different risk profile, but it still applies history on evidence the tool inferred, which is the line `plan/SyncAction.scala:295-318` draws and should keep drawing.

**Shortening the key to the marked heading alone.** Attractive because it collapses the largest blast radius. It does not survive: it reintroduces the collision the ancestor chain exists to prevent, it is not expressible for table cards (which key deeper than the marked heading), and it is on the do-not-relitigate list (HANDOFF.md:249). Rejected on the collision, not on the migration cost — the migration is a tag rewrite and is cheap, and saying otherwise would concede the one property the identity design was built to buy.

**A minimal-disambiguating-suffix key.** Makes a card's identity depend on which *other* headings exist in the file, so adding an unrelated sibling elsewhere moves a key with no edit to that card. Converts a visible local cause into an invisible non-local one — strictly worse than the problem.

**Anki's own note GUID as identity.** Not reachable: `notesInfo` returns noteId, profile, tags, fields, modelName, mod and cards, and the string `guid` does not occur in the add-on at all (VERIFIED, `__init__.py:1729-1737` plus a grep). But this is *not* the reason the door is shut, and the brainstorm briefly presented it as though it were: what forecloses an Anki-side identifier is the write-back rule, and the note *id* — which is what both rival Obsidian plugins key on — **is** returned. Manufacturing a second closed door in front of the real one is the kind of move this document should not make.

**The cloze-label-generalises argument for heading anchors.** Dropped, with reasons, at §4C. The anchor option itself survives, on different grounds and pending M1.

**Treating `.apkg` export as the backup answer.** The mechanism exists and is worse than absent: per-deck, `includeSched=False` by default, `False` on a missing deck rather than an error (VERIFIED, `__init__.py:2122-2133`). An export taken through the obvious call is a plausible-looking, silent, historyless snapshot. If a pre-run checkpoint is ever wanted, this is not it without M8.

**Reframing every silent hazard as silent.** Several of the risks surfaced in this brainstorm were rated silent against a report line built five days ago to end exactly that silence: `Report.parkedNote` prints the parked count and the word "suspended" on every run, including runs that would otherwise print `nothing to do` (`cli/Report.scala:108-117`; IN-FLIGHT.md:160-170). The residual claim is narrower and still worth making — **the run that does the damage is the silent one, and the exit code stays 0 forever after** — and that is what §3.4 says.
