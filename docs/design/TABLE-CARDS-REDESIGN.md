# Table cards: one note per row, so that siblings exist at all

_Written 2026-08-28, from a design conversation between Marc and Claude. **Nothing here is
built.** Claims marked MEASURED were established against a live collection in the
`claude-POC-test` profile and are recorded with their versions in
`docs/findings/ANKICONNECT-BEHAVIOUR.md`; everything else is reasoning, and says so. It follows this
repository's convention of opening with the answer rather than the three-layer TLDR / Summary /
Full form, because its siblings — `EVOLVABILITY.md`, `CLOZE-REDESIGN.md`,
`PARSER-DISAGREEMENTS.md` — do._

---

## The one-paragraph answer

Anki can hold two cards that test the same fact apart so you do not meet both in one sitting. It
calls them **siblings** and defines them strictly as **cards generated by the same note**. This
tool makes every table cell its own note, so no two cards from a table are ever siblings and the
setting cannot reach them — while a row card prints, on its answer side, the answer to every cell
card in that row. **Making one table row into one note fixes this, and the measurements needed to
know whether Anki cooperates have now been taken.** The obstacle is not the note type: it is that
Anki attaches review history to a template ordinal, so deciding which column occupies which slot
becomes a decision that can silently move history. The way out is that the note must store each
column's header anyway in order to print it, so Anki itself records what each slot currently
means. The cost that cannot be avoided is that every table card in an existing collection loses
its history once.

## 1. Why this cannot be fixed where it stands

**Siblinghood is not something this tool can express.** It is note membership, decided by the note
id in Anki's database. No tag, field or AnkiConnect call creates it between two notes. So this is
not a property that was captured badly; it is one that was never available under the current
packaging.

**What the current packaging produces.** `extract/Tables.scala` emits one `CardSpec.ThreeField` per
usable cell, keyed `…/{row concept}/{column header}`, and one `CardSpec.TableRow` per row carrying
two or more descriptors, keyed `…/{row concept}`. Each is one Anki note. A four-row,
three-descriptor table under a bare `#flashcard/table` marker therefore mints sixteen independent
notes.

**Burying does still work, in one place only.** A cell card is an `Obsidian Concept-Descriptor`
note. Under the default directions that a bare `#flashcard/table` yields, its first two templates
generate and the third stays behind `{{#ThreeWay}}`, so a cell card has exactly one sibling and
Anki will space the pair. A row card is a plain `Obsidian Basic` with one template and therefore
has no siblings at all, ever.

**The interference this leaves open is the one `docs/reference/LEARNING-MODEL.md` already argues about.**
Its section "Siblings must not share a session" makes an interference claim rather than an
ordering one: a fact asked several ways produces several cards, and each card's answer is printed
on its siblings' prompts. A row card and its own cell cards are the sharpest possible instance,
and they sit on unrelated schedules with nothing able to relate them.

**It is also a fork this repository already recorded and took without noting that it had.**
`docs/design/CLOZE-REDESIGN.md` weighs one note per block against one note per label-group in a table
whose last row reads *Anki sibling burying: kept / lost*. Tables are on the lost side, and nothing
records that as a decision.

## 2. What the measurements license

All four are recorded with their versions in `docs/findings/ANKICONNECT-BEHAVIOUR.md`. Two of them
reproduce M5's flip half, already run on 2026-08-26; the round trip is the genuinely new one.

- **Anki publishes its own generation rule.** `createModel` returns a `req` array stating, per
  template, which fields must be non-empty for that template to produce a card. Conditional
  generation is therefore inspectable rather than inferred from template text.
- **Widening is an ordinary field update.** MEASURED: filling a previously empty gate field on an
  existing note generates the new card, and every existing card keeps its id, ordinal, review
  count, due timestamp and queue. No note type change, no new note, no history moved.
- **Narrowing strands rather than destroys.** MEASURED: emptying the field leaves the card in
  place with its history, rendering Anki's own blank-front placeholder, until a person runs Tools
  then Empty Cards. There is no add-on action for that.
- **The round trip is lossless.** MEASURED: restoring the column returns the same card id,
  ordinal, review count and due timestamp.

## 3. One capped-width note type, not a family of fixed-width ones

The obvious shape, and the one Marc proposed, is Scala's `Tuple2 … Tuple22`: a note type per
arity, the arity read off the column count, and a refusal above the cap. Reading the arity off the
table is right, and consistent with `model/Marker.scala`'s own argument that a marker must name
only what the tool cannot see. Refusing above the cap is right too, and needs no new argument:
`SpecError.TableWithoutDescriptors` is the same shape.

**The split itself is wrong, because Anki has the feature Scala lacked.** Scala needed the family
because it could not abstract over arity. Anki's conditional generation means the widest type
already behaves as every narrower one, and this repository already ships two templates that rely
on it. So the family buys types the wide one subsumes, and pays for them:

| | manifests | templates | HTML files |
| --- | --- | --- | --- |
| one type per arity, 2 to 6 | 5 | 45 | 90 |
| one capped type at 6 | 1 | 13 | 26 |

**The decisive cost is not files, it is retypes.** `Tuple2` and `Tuple3` are unrelated types, so
adding an element produces a different type rather than a bigger one. Under the family, adding a
column would change the note type of every row in the table, firing `SyncAction.Retype` across the
whole table for the commonest edit there is. That lands on the one thing still unmeasured in this
area: whether a retype makes Anki generate a card that did not exist before. The capped type never
retypes, and its widening path is measured.

## 4. The placement problem, which the packaging choice does not touch

Anki attaches scheduling to a card, and a card is identified inside its note by which template
produced it. So each column must occupy a numbered slot, and the scheduling follows the slot.

**Assign slots by position and history moves silently.** A table with `Cost` and `Benefit`,
reviewed for six months. Insert `Risk` between them, and by position `Risk` takes slot two while
`Benefit` slides to three. The card at slot two already holds six months of scheduling earned
asking about `Benefit`, and now asks about `Risk`; `Benefit` starts over at slot three. The tool
sees a note whose fields changed, which is an ordinary update. Anki sees the same. Nothing
complains.

**Today this cannot happen**, because a cell card is keyed by its column header text and position
plays no part in identity. Reordering a table's columns changes no key at all. That property must
survive the redesign or the redesign is a regression.

**Rows are not affected either way.** A row is keyed by its concept cell, so inserting and
reordering rows is safe. This is a columns-only problem.

## 5. The placement answer: read what the note already records

The note must carry `Header1..HeaderN` regardless, because the card prints the column name. **So
Anki itself holds the answer to what each slot currently means**, and `ObservedNote.fields` is
already fetched and already in the planner's hand when it decides update versus create.

> **CORRECTED 2026-08-28 BY BUILDING IT** (`spike/RowPlacement.scala`). This section originally
> said a slot needs two fields, a header and a value. **It needs three.** Matching on the
> DISPLAYED header would make placement depend on the renderer: headers are escaped for HTML
> today, and `extract/Tables.scala` records that rendering a cell's STRUCTURE — bold, inline
> code — is a later slice. Escaping is injective so matching would survive it; rendering
> structure is not, so matching would not. A renderer change would then move placements, and a
> moved placement moves review history — the very coupling that file was split to prevent.
>
> **So the frozen key must be its own field per slot, beside the displayed header, and it must be
> there in the first version.** Added later it cannot recover the placements already made without
> it.

The rule: **place each column into the slot whose stored header matches it**; new columns take
free slots; fall back to position when there is no existing note, which is safe because there is
no history to protect. Reordering then changes nothing, insertion changes nothing for existing
columns, and the swap in §4 stops being representable rather than merely being detected.

> **"FREE" IS NARROWER THAN IT LOOKS, and getting it wrong reintroduces the whole problem.**
> _Found 2026-08-28 by a test in `spike/RowPlacement.test.scala`, against an implementation that
> had it wrong._
>
> The first version read a free slot as one no KEPT column had claimed. That let a newcomer take
> a slot being VACATED in the same placement — and a vacated slot's card **is not gone**. It sits
> there blank-fronted holding the removed column's history, per §2. Refilling its gate field hands
> that history to a different question, silently. Rename a column and the replacement would have
> inherited its predecessor's schedule, which is §4's failure reached by a friendlier route.
>
> **A slot is free only when Anki records nothing at it.** The consequence is worth stating
> plainly: a table can run out of slots while appearing to have spare columns, because stranded
> cards occupy them. Only a person can release those, through Tools then Empty Cards, so this has
> to be a refusal that names the remedy rather than something the tool works around.

**This does not make identity a function of Anki, and the distinction is the whole argument.** The
card's key stays a pure function of the vault. Only which slot a column occupies is read from the
artifact about to be overwritten, which is what an executor does. The standing position that a
sidecar is a cache and never an oracle is not engaged, because nothing is remembered between runs.

**It also removes two worse options** that existed only to make placement derivable without
looking at Anki: authors numbering their table headers by hand, in the manner of cloze labels, and
hashing a header into a slot with a collision refusal that would look arbitrary from the outside.

**One consequence to name rather than bury.** Placement now depends on collection state, so the
same vault synced into two collections could order its slots differently. `README.md`'s
one-vault-per-profile rule already covers this, and the cards are the same set either way.

## 6. The two open items

### 6.1 A deleted column leaves a blank card, and the tool cannot clear it

MEASURED, §2. The card keeps its history and renders Anki's blank-front placeholder until a person
runs Tools then Empty Cards.

**This repository has already ruled on this exact shape, and the ruling should be inherited rather
than reopened.** oas-jco covers a card retired by narrowing a marker, which strands
one card of a note whose other cards are healthy. The decision was a per-card flag in colour
seven, on the grounds that Anki tags live on notes rather than cards, so a note-level tag would
mark healthy siblings too, and that bare suspension would leave the tool unable to recognise its
own work later.

**One caveat, and it is load-bearing.** That entry closes by dismissing suspension on the grounds
that "a retired card's front renders empty and Anki never queues it". The 2026-08-28 measurement
found the stranded card keeping its queue value and its due timestamp, which points the other way.
Nobody has established whether the scheduler actually presents such a card. Until that is run, the
ruling stands but its stated reason does not.

_Also worth carrying across: do not reach for the add-on's `removeEmptyNotes` here. It deletes
note types whose use count is zero and touches no cards at all._

### 6.2 A renamed column header loses its card's history

Placement matches stored headers against vault columns, so a rename matches nothing. The tool
cannot distinguish a rename from a deletion plus an addition, because both leave the vault in an
identical state. The renamed column takes a free slot and starts from zero, and the old slot goes
blank, feeding straight into §6.1.

**This is the cost `README.md` already declares and accepts** for renaming a marked heading, and it
should be documented in the same terms rather than treated as a fresh defect.

**Marc's proposal — infer the rename from what did not change — is already this repository's
strongest recovery candidate**, and it is stronger for tables than for the case it was written
for. `EVOLVABILITY.md` §4A, "exact non-`Context` field pairing, report-only", makes the reframe
that matters: exact agreement on a byte-identical field is **evidence of the same class as the
content hash**, not a similarity score, so the standing rule that fuzzy matching may rank but never
apply is not engaged.

That section explicitly excludes tables, on the grounds that "a table's cells come from rows, not
headings". **Under this redesign that stops being true.** A renamed column leaves the row concept
and every value byte-identical and changes exactly one header field, so the evidence says not
merely that something matches but precisely what moved.

The constraints carry over unchanged, and there is a working precedent for the shape in
`plan/SyncAction.scala`'s suggestion text: speak only when exactly one candidate matches, stay
silent at zero or several, print the exact tag to apply, and never apply it.

**Git is a second, independent witness, and should not be waited for.** The git-as-rename-evidence
route in `CLOZE-REDESIGN.md` would cover this too, but it is blocked because the vault is not a
repository. Field pairing needs no git, costs no additional Anki calls, and works retroactively on
cards that are already stranded.

## 7. The cost that cannot be avoided

**Every table card in an existing collection loses its history once.** Anki has no operation that
merges notes, and a card cannot move between notes, so repackaging a row means creating one note
and orphaning the cells that used to cover it.

**This is the argument for deciding now rather than later, and it is `EVOLVABILITY.md` §7's
governing fact rather than a new one.** That section observes that the collection is nearly empty
today, which makes exactly one class of work free now and expensive later: work that touches
stored data, naming *what shape the note types are* as an instance. This redesign is precisely
that class. Its price is the smallest it will ever be, and it grows with every card reviewed
between now and whenever it is decided.

## 8. What this document does not decide

**Whether to do it at all.** The measurements say the mechanism works and the design is
expressible. They say nothing about whether sibling burying on table cards is worth one-time
history loss on every table card, which is a judgement about how Marc studies rather than about
what Anki does.

**The cap.** Six columns is used above for arithmetic, not proposed. The number should come from
looking at the real vault's widest table, which nobody has done.

**Whether the row card stays a separate card kind.** Under this design the row card becomes one
more template on the same note, the one that blanks every value, which is what makes a `Both`
table's cards siblings of each other. That is assumed throughout and has not been argued
separately.
